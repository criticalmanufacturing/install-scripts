# SaaS Connector Ubuntu operations

The installer follows the Ubuntu VM runbook with Bash and ordinary Ubuntu tools.
It installs `curl`, `ca-certificates`, `tar`, `podman`, `uidmap`,
`dbus-user-session`, and `netcat-openbsd`. The Skupper CLI is pinned to **2.2.3**
and its release archive is checked against the expected SHA256 digest.

## Setup and options

Use a normal user with sudo access, a direct SSH/console login, and a working
systemd user session on Ubuntu 24.04 or 26.04 LTS. Rootless Podman requires
subordinate UID/GID ranges, normally assigned when Ubuntu creates the user.
The VM needs access to Ubuntu mirrors, GitHub release assets, Quay images, the
cloud link endpoint, and the application.

Required answers are link file path, connector name, application IP, and
application port. Each can be supplied as an option instead of a prompt.
The site name defaults to the machine's hostname in lowercase, and the cloud
hostname is read from the first endpoint in the generated Link YAML.
Exported setup variables are retained; command-line options override them.
The site, namespace, and connector names use lowercase letters, digits, and
hyphens, with at most 63 characters.

| Optional argument | Behavior |
| --- | --- |
| `--site-name NAME` | Defaults to the machine's hostname in lowercase |
| `--cloud-ip IP` | Add an ingress IP override for the cloud hostname |
| `--cloud-host HOST` | Override the hostname inferred from the Link YAML |
| `--routing-key KEY` | Defaults to the connector name; must match the cloud Listener |
| `--namespace NAME` | Defaults to `default`, matching manual Skupper commands |
| `--timeout SECONDS` | Wait up to this many seconds for Site/Link readiness; default 180 |

There is no dry-run mode or custom YAML validation. Skupper imports the supplied
Link/Secret YAML. A shell check extracts the first Link endpoint hostname,
including quoted values and Windows line endings. If it cannot find one, supply
`--cloud-host` explicitly. Use a trusted link file generated by the cloud
administrator; it contains private credentials. Setup sets its permissions to `600`.

The cloud hostname and ports remain as supplied in the link file. Without an IP
override, existing name resolution is used. With an override, setup adds the
hostname/IP to `/etc/hosts` before creating the site. A matching entry is reused;
a conflicting entry stops setup with instructions to correct it. Existing aliases
and other entries are left in place.

## Reruns and existing sites

To expose an additional app, reuse the link file, site, and namespace with a new
connector name and the app's address and port. Existing connectors remain in
place. The cloud needs a matching Listener. See the
[additional-app command](README.md#expose-another-app).

For a retry or an update, reuse the same site, namespace, and connector names.
Setup reuses an existing
Site input file, reapplies the supplied Link YAML, and updates an existing
Connector's host, port, and routing key. Changing names can create additional
resources. Nothing is deleted automatically.

The previous script generated site/namespace names such as
`vm-ubuntu-3ff529abb032`. Pass the original site name with `--site-name` and its
namespace with `--namespace` to continue that installation. For example, an
earlier script attempt using namespace `asm` needs `--namespace asm`. Manual
commands without a namespace use `default`, even when the site is named `asm`.

Skupper is installed with `--reload-type auto`. The controller applies resource
changes; the script does not call `system start` or `system reload`. It enables
the user Podman socket, lingering, the Podman restart service, and the Skupper
controller service for operation after logout and reboot.

Changing a hosts entry does not update an existing container's copy of
`/etc/hosts`. For a previously created router, review its mapping and Podman logs
before performing any manual recreation. The script does not force a router
reload or remove containers as a recovery action.

## Check a deployment

The Site must reach `Ready` before import. Setup then imports the link, displays
its current status, and creates or updates the Connector before waiting for the
Link to reach `Ready`. The wait prints status changes and a progress update at
least every ten seconds. A timeout identifies the namespace's router log command.
`Site not initialized yet` can appear briefly while the controller starts; a
subsequent Ready status means that initialization completed.

The script checks the Podman socket and uses a TCP probe for the application,
so it works for HTTP and other TCP services. Skupper stays pinned to 2.2.3 instead
of using the rolling installer. OpenSSL and HTTP-specific checks are not required
or run. A completed setup alone does not prove application traffic. From a cloud
client, send a real application request to the matching Listener Service to verify
the connection end to end.

Set `LOCAL_NAMESPACE` to the namespace printed by setup:

```bash
"$HOME/.local/bin/skupper" --platform podman --namespace "$LOCAL_NAMESPACE" site status
"$HOME/.local/bin/skupper" --platform podman --namespace "$LOCAL_NAMESPACE" link status
"$HOME/.local/bin/skupper" --platform podman --namespace "$LOCAL_NAMESPACE" connector status
systemctl --user status podman.socket skupper-controller.service
journalctl --user -u skupper-controller.service --no-pager -n 50
podman ps -a --filter name=skupper
podman logs --tail 50 "${LOCAL_NAMESPACE}-skupper-router"
```

For `Failed to stop container`, inspect Podman logs and the container state before
any manual removal. For a Pending link, check hostname resolution, the port in
the Link YAML, outbound firewall access, and the TLS endpoint. Ingress must pass
Skupper TLS through without replacing its certificate. For an unreachable
application, check the address and port from the VM with `nc -z -w 5 IP PORT`.

The CLI is at `~/.local/bin/skupper`. State defaults to
`~/.local/share/skupper`. Protect that directory and the supplied link file;
do not share credentials or run setup with shell tracing.

## Development checks

```bash
bash -n saas-connector/setup-saas-connector-ubuntu.sh
bash -n saas-connector/tests/test_ubuntu.sh
shellcheck -x -S style saas-connector/setup-saas-connector-ubuntu.sh saas-connector/tests/test_ubuntu.sh
bash saas-connector/tests/test_ubuntu.sh
```

The Bash tests use isolated state and replace host-changing commands. They cover
terminal prompts with a streamed script, options, first setup, retries, connector
updates, and failure handling. Set `SAAS_CONNECTOR_TEST_CLI` to a verified 2.2.3 executable
to also check resource imports and updates against the real CLI, without starting
Podman. CI performs that check too. No Python is used by the tests or workflow.

Full VM checks remain in [tests/acceptance.md](tests/acceptance.md).
